# 「小さな判断」の自動化パッケージ（Jev 前提・企画メモ）

社内向けの企画メモ。サイト（`/business`）にはまだ載せていない。
金額はすべて**受注実績のない暫定値**。Jev の数字は 2026-09 時点の公開情報で、日本語での精度は未検証。

---

## 1. 何が変わったのか（正直な整理）

Jev（TypeSafe AI、2026-09-15 早期アクセス開始）は文章を返さないモデル。
状態（テキストか JSON）と「型付きの問い」を渡すと、次のどれかを **確信度つき** で 70〜500ms で返す。

| 問いの型 | 返ってくるもの | 例 |
| --- | --- | --- |
| Choice | 選択肢のどれか | 問い合わせの種別 = 見積 / 不具合 / 採用 / 営業 / その他 |
| Score | ルーブリックの点数 | 緊急度 1〜5 |
| Noul | yes/no の確率 | 「返信が必要か」= 0.93 |

料金は入力 100 万トークンあたり $0.042、出力は無料。

**中小企業向けで効くのは、実は料金ではない。** 月 3,000 件の判断で比べると:

| | 月額の目安 |
| --- | --- |
| Jev（1 件 1,500 トークン × 3,000 件） | 約 $0.2 |
| Claude Haiku 4.5（同条件、出力 100 トークン） | 約 $6 |

中小企業の件数なら、LLM でももともと月 1,000 円もかからない。
これまで「割に合わない」と言われていた理由は API 代ではなく、次の 2 つだった。

1. **間違えたときが怖い。** LLM の自己申告の確信度は当てにならず、「自動で流していいもの」と「人が見るべきもの」を線引きできなかった。だから結局ぜんぶ人が見ることになり、効果が出なかった。
2. **作るのに手間がかかる。** 自由文で返ってくる答えを解析し、揺れを吸収する処理を案件ごとに書いていた。10 万円の案件には収まらなかった。

Jev は **確信度が較正されている**（確信度が高いほど実際の正答率も高い、と訓練されている）ので 1 が、**型で返る**ので 2 が解ける。
売り文句は「安い AI」ではなく「**自信があるものだけ自動で流し、迷ったものだけ人に回す仕組み**」。

## 2. パッケージの形

### 共通の骨組み（全パッケージで同じもの）

```
入口（Gmail / フォーム / スプレッドシート）
  → 判断（Jev。使えない場合は Claude Haiku 4.5 の構造化出力）
  → 確信度で 3 つに分ける
       高い   … 自動で処理（通知・振り分け・記入）
       中くらい … 「要確認」シートへ。人がワンクリックで確定
       低い   … 何もせず人に渡す
  → 判断ログ（入力・答え・確信度・人の修正）をシートに残す
```

- 画面は作らない。**お客さんが今使っているスプレッドシートが管理画面**になる。
- 判断を行う部分は差し替えられるように作る。Jev が日本語で使えない場合や、早期アクセスの鍵が取れない場合は Haiku に切り替える。どちらで動かしても、お客さんに見える部分は変わらない。
- 人の修正ログがたまるので、月に 1 回しきい値を見直す。これが保守契約の中身になる（後述）。

一度作れば、パッケージごとに変わるのは「問いの定義」と「処理の出口」だけ。2 件目以降の案件は作業の大半が設定で済む。

### パッケージ（まずこの 3 つ）

`/business` の「よくある作業」との対応を右の列に書いた。

| # | 名前 | 判断すること | 出口 | 対応する「よくある作業」 |
| --- | --- | --- | --- | --- |
| A | **問い合わせの仕分け** | 種別（Choice）・緊急度（Score）・返信が必要か（Noul）・定型で返せるか（Noul） | Slack / Chatwork の担当チャンネルに通知、定型なら返信の下書きを作る | 問い合わせを手で写している／同じ質問に毎回返信している |
| B | **口コミ・アンケートの仕分け** | 良い/悪い（Choice）・話題（Choice、複数）・返信すべきか（Noul） | 集計シートに記入、悪いものは即通知、月次でまとめを作る | 毎朝サイトを開いて数字をメモしている／月末の集計 |
| C | **書類の「要確認」チェック** | 読み取った請求書・注文書が、マスタや過去の取引と比べて不自然でないか（Noul × 数問） | 問題なしは記録だけ、怪しいものだけ担当者に回す | FAX や PDF の注文書を打ち直している／請求書を 1 件ずつ見ている |

C の PDF 読み取りは Jev ではできないので、読み取りは既存の OCR か Claude で行い、Jev は読み取った後の「おかしくないか」の判断だけを受け持つ。

**やらないもの：** 採用の合否、与信、医療・法律の判断のように、間違ったときに人が不利益を受けるもの。
「一次の仕分けだけ」という形でも受けない。最終判断を人がするという建前でも、実際には自動の判断に引きずられるため。

## 3. 料金（暫定）

いまの料金表の範囲に収める。新しい料金体系は作らない。

| | 金額 | 中身 |
| --- | --- | --- |
| 導入（A・B・C のどれか 1 つ） | **10 万円**（「ひとつ自動化」） | ヒアリング、問いの定義、接続、しきい値の初期設定、手順書 |
| 2 つ目以降 | 5〜8 万円 | 骨組みを使い回せるぶん安くする |
| 保守（任意） | **月 15,000 円**（既存の保守と同じ） | 月 1 回、判断ログを見てしきい値と選択肢を直し、**自動で処理できた割合と正答率をレポートにする** |
| API 代 | 実費（月数百円程度） | お客さんのアカウントで契約してもらうのが基本 |

保守の中身が「壊れたら直す」から「**毎月、自動で処理できる割合が増えていく**」に変わる。この種の案件では、これが保守を続けてもらう理由になる。

## 4. すぐ動けること（順番どおり）

1. **Jev の早期アクセスに申し込む。** 鍵が取れるまで順番待ち。取れない間は Haiku で作り、あとから差し替える。
2. **日本語で精度を確かめる（半日）。** A の問い合わせ文を 50 件自作して、Jev と Haiku を比べる。見るのは正答率だけでなく、**確信度が 0.9 を超えた問いの正答率**。ここで Jev の較正が日本語でも効いているかが分かる。効いていなければ、この企画書の前提は崩れる。
3. **A をデモにして `/business` に置く。** 既存のデモと同じく、ブラウザの中で動く見本にする（見本の問い合わせを選ぶと、仕分け結果と確信度が出る）。デモの中では判断を事前計算した結果にして、API は叩かない。
4. **モニターの 3 社枠を A で使う。** 既存のモニター枠（半額）をそのまま使う。

## 5. リスクと未確認のこと

- **日本語での精度は不明。** 公開されている評価は英語ばかり。上の 2 で確かめるまで、お客さんに Jev の名前を出して約束しない。
- **早期アクセスの段階。** 料金・仕様・提供条件が変わりうる。自分で動かす（セルフホストする）手段もない。判断部分を差し替えられる作りにしているのはこのため。
- **データの送り先。** 米国のスタートアップにお客さんの問い合わせ文を送ることになる。秘密保持契約とデータの取り扱い（保持期間・学習に使われるか）を、TypeSafe の規約で確認してから提案する。個人情報を含む場合は、送る前に伏せる処理を入れる。
- **較正は「全体として」の話。** 1 件ずつの確信度が必ず正しいわけではない。人が見る枠をなくす売り方はしない。
