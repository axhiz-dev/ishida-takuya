# 書類チェッカー（パッケージ設計メモ）

`docs/jev-package.md` のパッケージ C を、1 社ごとの作り込みではなく **設定で使い回せる製品** にするための設計メモ。
金額はすべて**受注実績のない暫定値**。サイト（`/business`）にはまだ載せていない。

---

## 1. 一言でいうと

> 届いた請求書を、払う前に一度見てくれる係。
> 問題のないものは記録だけして通し、おかしいものだけ理由つきで人に回す。

最初は **受け取った請求書（支払う側）** に絞る。

- 業種を問わず、どの会社にもある。
- インボイス制度で、確認する項目が増えた（登録番号、税率ごとの消費税）。
- 「振込先が変わりました」という詐欺メールが実際に起きていて、経営者に説明しやすい。
- 間違ったときの損が金額で見えるので、効果を説明しやすい。

注文書、納品書、経費の領収書は、同じ骨組みに書類の種類を追加する形で広げる（§6）。

---

## 2. 汎用にできる理由

「要確認かどうか」を決める材料は、会社が違ってもほとんど同じだから。
会社ごとに違うのは **どのチェックを使うか** と **照合先のデータ（マスタ）** だけで、チェックの中身は共通にできる。

そこで、製品の中身を次の 3 つに分ける。

| | 中身 | 会社ごとに変わるか |
| --- | --- | --- |
| **骨組み** | 取り込み → 読み取り → チェック → 仕分け → 記録 | 変わらない |
| **チェックの一覧** | 下の §3。約 20 項目 | 変わらない（使う・使わないを選ぶだけ） |
| **設定ファイル** | 使うチェック、しきい値、マスタの場所、通知先 | 会社ごとに 1 枚 |

2 社目以降の導入は、ほぼ設定ファイルを書くだけで済む。これで 10 万円に収まる。

---

## 3. チェックの一覧

**AI に判断させるのは最後の手段にする。** 計算で確かめられるものは計算で確かめる。
そのほうが正確で、「なぜ要確認なのか」をお客さんに説明できる。

| 系統 | チェック | 何でやるか |
| --- | --- | --- |
| **計算** | 明細の合計が小計と合っているか | コード |
| | 税率ごとの消費税が正しいか（8% / 10% の混在、端数処理） | コード |
| | 小計＋税＝合計になっているか | コード |
| **形式** | 適格請求書の登録番号があるか、形式が正しいか（T＋13 桁） | コード |
| | その番号が国税庁の公表サイトに実在し、社名と一致するか | 国税庁の Web-API（要申請） |
| | 宛名が自社か、支払期日が過ぎていないか、発行日が未来になっていないか | コード |
| **照合** | 取引先マスタにある会社か（表記ゆれも同一とみなす） | コード＋Jev（同一か：Noul） |
| | **振込先口座がマスタと違わないか** | コード |
| | 発注書・見積書と金額・品目が合っているか | コード＋Jev（同じ品目か：Noul） |
| **履歴** | 同じ請求がすでに来ていないか（番号・金額・日付） | コード |
| | その取引先の過去の金額から大きく外れていないか | コード（統計） |
| | 初めての取引先か | コード |
| **中身** | 品目が、その取引先との普段の取引内容と違わないか | Jev（Noul） |
| | 備考に「口座変更」「至急」など、注意すべき言葉がないか | Jev（Choice） |
| | 品目の勘定科目の候補 | Jev（Choice） |

計算系のチェックには、**読み取りミスを見つける役割** もある。
読み取りを間違えると合計が合わなくなるので、請求書側のミスでも読み取りのミスでも、どちらにしても人に回る。
AI の読み取りを信用しすぎない仕組みを、製品の中に組み込んでいることになる。

### 仕分けの結果

各チェックは「OK／要確認／NG」と理由を返す。書類 1 枚の判定は次のとおり。

- **通してよい** … 全部 OK。記録だけする。
- **要確認** … どれかが要確認。理由を並べて担当者に通知する。
- **止める** … 振込先の不一致、二重請求の疑いなど、払ってから気づくと取り返しがつかないもの。目立つ通知にする。

どのチェックを「止める」扱いにするかは、設定ファイルで会社ごとに決める。

## 4. 構成

```
取り込み        Gmail の特定ラベル / Google ドライブの特定フォルダ / スキャナの保存先
  ↓
読み取り        Claude（画像・PDF → 決まった形の JSON：取引先・番号・日付・明細・税・合計・振込先）
  ↓
チェック        §3 の一覧を設定どおりに実行（コード → 国税庁 API → Jev の順）
  ↓
仕分け・通知    スプレッドシートの一覧に 1 行追加、要確認と止めるは Slack / Chatwork / メールで通知
  ↓
記録            判定・理由・人の修正をシートに残す（しきい値の見直しに使う）
```

- **第 1 版は Google Workspace を使っている会社に限る。** Microsoft 365 の会社には、需要が確認できてから対応する。
- **画面は作らない。** 結果の一覧はスプレッドシート。担当者は「確認済み」の列にチェックを入れるだけ。
- **書類の保存はしない。** 保存は、お客さんがいま使っている仕組み（ドライブや会計ソフト）のまま。電子帳簿保存法の要件を満たすとは言わない（保存の責任を持たないため）。
- **読み取りと判断に使う AI は差し替えられるようにする。** Jev が使えない間は、判断も Claude で行う。

### 運用コスト（月 300 枚の場合）

| | 1 枚あたり | 月 300 枚 |
| --- | --- | --- |
| 読み取り（Claude Sonnet 5 の場合。入力 2,500・出力 800 トークンで試算） | 約 $0.013 | 約 $4 |
| 判断（Jev） | ほぼ 0 | 1 円未満 |

月 1,000 円もかからない。お客さんの API アカウントで払ってもらう。

## 5. 既存の製品との違い

請求書の受け取りサービス（Bill One、バクラクなど）は、読み取りもチェックもすでに持っている。
正面からは勝てないので、**そこを入れない会社** を狙う。

| | 請求書受け取りサービス | このパッケージ |
| --- | --- | --- |
| 料金 | 月額（数万円〜） | 導入の買い切り＋任意の保守 |
| 業務の変え方 | 受け取り方法を変え、取引先にも案内する | 今の受け取り方のまま、手前に置くだけ |
| チェック項目 | 製品が決めたもの | 会社ごとに選べて、足せる |
| 向いている会社 | 月数百枚以上 | **月 30〜300 枚** で、専任の経理が 1〜2 人 |

「専用サービスを入れるほどではないが、社長か経理 1 人が毎月全部見ている」会社が相手になる。

## 6. 料金とメニュー（暫定）

いまの料金表の中に収める。

| メニュー | 金額 | 中身 |
| --- | --- | --- |
| **標準** | 10 万円（ひとつ自動化） | 受け取った請求書 1 種類。計算・形式・履歴のチェックと、取引先マスタ・振込先の照合 |
| **照合つき** | 30 万円（つながる自動化） | 標準に加え、発注書・見積書のデータとの照合（発注データの置き場所に合わせてつなぐ） |
| **書類の追加** | 5〜8 万円／種類 | 注文書・納品書・経費の領収書など |
| **保守（任意）** | 月 15,000 円 | 月 1 回、判定の記録を見てしきい値とチェックを直す。「止めた件数」「要確認の件数」「人が直した件数」を月次で報告する |

導入の流れは今の「進め方」と同じ。
ヒアリングで最初に見せてもらうのは、**過去 3 か月分の請求書と、実際にあったミスの例**。ミスの例がそのままテストデータになる。

## 7. 先にやること

1. **見本の請求書を 5 枚作る。** 正常、税の計算ミス、二重請求、振込先の変更、登録番号なし。
2. **読み取りの精度を確かめる。** 見本に加え、手書き・FAX・スキャンの傾きがあるものを含めて 30 枚ほど。計算系のチェックで読み取りミスが拾えるかも見る。
3. **国税庁の Web-API の利用を申請する。** アプリケーション ID の発行に時間がかかるため、先に出しておく。
4. **`/business` にデモを置く。** 見本の 5 枚を選ぶと、チェックの結果と理由が一覧で出るもの。既存のデモと同じく、ブラウザの中だけで動かす。読み取り結果は事前に用意したものを使い、API は叩かない。
5. **モニター枠（半額）を、この標準メニューで使う。**

## 8. 決めておくこと・リスク

- **責任の範囲。** 「チェッカーを通ったから払った」で損が出たときの扱いを、契約書に書く。位置づけは「一次チェック。支払いの判断は人がする」。
- **振込先などの情報を外部の AI に送ること。** Claude の API の取り扱いをお客さんに説明する。Jev には、読み取ったあとの判断に必要な項目だけを送り、口座番号は送らない（口座の照合はコードで行う）。
- **読み取りが難しい書類。** 手書きや画質の悪い FAX は、読み取りの時点で要確認に回す。「全部読めます」とは言わない。
- **しきい値の初期値。** 最初の 1 か月は要確認に多めに回るように設定し、記録を見ながら減らしていく。その前提を導入時に伝えておく。
