## 6. デモの刷新

### 6-1. 方針
- 今のデモは「ツールの機能紹介」寄り。これを **「ある担当者の毎日の作業が、どう変わるか」という具体的なシナリオ** に作り替える。
- 3本とも同じ流れ（下記）にそろえ、見る人が「うちの○○も同じだ」と重ねられるようにする。
- 入口のオフィスのイラスト（`public/business/office.webp`）は「集計に悩む人」「書類を確認する人」「問い合わせに対応する人」の3人。**3本のシナリオはこの3人に対応させる**（イラストを作り直さずに済むように）。

### 6-2. 各デモの共通の流れ

| 段階 | 見せること | 操作 |
|---|---|---|
| ① いつもの朝 | 担当者が毎日やっている手作業の手順と、それぞれにかかる時間（合計◯分） | 手順を眺める・元のファイルやメールを開いてみる |
| ② 組み合わせて自動化 | どの部品（ファイル取り込み、ルールでの整理、AIの下書き、通知など）を組み合わせるか。**どこがルールで、どこがAIかを区別して表示** | 「実行」を押すと、見本データが実際に変換されていく |
| ③ 人が確認する | 自動では決めきれなかったものだけが残る。AIの出力は「下書き」「候補」と明記 | 要確認の項目を選んで確定する |
| ④ 結果 | 「60分 → 5分」のような前後比較。数字は「例」と明記 | 結果を見る・保存する（CSVなど） |
| ⑤ 毎朝の自動実行 | 「平日 毎朝8:00に実行」を設定 → 翌朝、出社すると結果と通知が届いている画面 | 実行時刻を設定する・「翌朝」を再生する |

守ること：
- 見本データであることを常に表示する。実際の送信・保存・外部通信はしない。
- **処理中の表示は、画面上で実際に起きている変換だけを書く。** 例えば「日付の形式を揃えています」と書くなら、見本データに形式の違う日付を入れ、揃えた前後を見せる（今のデモはここが実態と合っていない）。
- 要確認の判定は見本データとマスタから導く。**特定の名前をコードに直書きしない**（今の `row.customer !== "みなと企画"` のような書き方をやめ、「マスタにない取引先」を計算で見つける）。
- AIが関わる部分は「送信」ではなく「下書き」「候補」で止め、最後は人が確定する流れにする。
- 各デモの最後は「この自動化を自社でも → 進め方と費用へ」でステップ2へつなぐ。
- 1画面に収めるための縮め方・演出はお任せ。⑤は時計が進む・通知が届くなどの演出があると伝わりやすい。

### 6-3. シナリオ案

**実装するのは A1・B1・C1 の3本（★）で確定。** その他の案は「参考・今回は実装しない」とし、将来差し替えるときの候補として残している。

#### A. 集計に悩む人（集計・レポート）

**★A1. 毎朝の売上日報**
- いつもの朝（例：60分）：店舗・EC・代理店から届く前日の売上ファイルを開く → 1つのExcelに貼り付ける → 取引先名の表記ゆれを手で直す → 重複を探す → 集計して前日比を計算 → 上司にチャットで報告文を書く
- 組み合わせ：ファイル取り込み（列名・日付形式をそろえる）＋顧客マスタでの名寄せ（ルール）＋重複チェック（ルール）＋集計（プログラム）＋前日比コメントの下書き（AI）
- 人が確認：マスタにない取引先、同じ伝票番号の重複
- 結果（例）：60分 → 5分（要確認の2件を見るだけ）
- ルーチン化：毎朝8:00に自動実行。出社すると日報と報告文の下書きがチャットに届いていて、要確認があるときだけ通知される
- 備考：今の集計デモのデータ・ロジックを最も流用できる

**〔参考・今回は実装しない〕A2. 勤怠の打刻漏れ・残業チェック**
- いつもの朝（例：45分）：勤怠システムから前日分をダウンロード → 打刻漏れと残業の多い人を探す → 一人ずつ確認の連絡を書く
- 組み合わせ：勤怠データの取り込み＋ルールでの抽出（打刻漏れ、月の残業が上限に近い人）＋本人宛て確認メッセージの下書き（AI）
- 人が確認：事情がありそうなケース（休日出勤の申請済みなど）
- 結果（例）：45分 → 5分
- ルーチン化：毎朝、対象者一覧と送る前のメッセージ下書きがそろっている

**〔参考・今回は実装しない〕A3. 在庫の確認と発注の準備**
- いつもの朝（例：40分）：在庫表を開く → 発注点を下回った商品を探す → 仕入先ごとに発注書を作る
- 組み合わせ：在庫データの取り込み＋発注点での抽出（ルール）＋仕入先ごとの発注書下書き
- 人が確認：急に売れ方が変わった商品（AIが「いつもと違う」と候補を出す）
- 結果（例）：40分 → 5分
- ルーチン化：毎朝、発注候補リストと発注書の下書きがそろっている

#### B. 書類を確認する人（書類・転記）

**★B1. 経費精算の領収書チェック**
- いつもの朝（例：60分）：社員がチャットに送ってきた領収書の写真を開く → 日付・金額・支払先を経費一覧に転記 → 勘定科目を判断 → 規程（上限額など）に合っているか確認
- 組み合わせ：領収書の読み取り（AI）＋経費一覧への転記＋勘定科目の候補（AI）＋規程チェック（ルール）
- 人が確認：読み取りに自信がない項目、規程の上限を超えているもの
- 結果（例）：60分 → 10分
- ルーチン化：毎朝、前日分が一覧になっていて、確認が必要な行だけ色が付いている
- 備考：業種を問わずどの会社にもある作業。領収書の見本画像はHTML/CSSで描いた架空のものでよい

**〔参考・今回は実装しない〕B2. 注文メールから受注台帳への転記**
- いつもの朝（例：60分）：夜のうちに届いた注文メール（書式がばらばら）を1通ずつ読む → 受注台帳に転記 → 在庫と納期を確認して返信
- 組み合わせ：メール本文からの項目抽出（AI）＋台帳への転記＋商品マスタとの照合（ルール）＋受付返信の下書き（AI）
- 人が確認：商品名が特定できない注文、数量が普段と極端に違う注文
- 結果（例）：60分 → 10分
- ルーチン化：出社すると夜間の注文が台帳に入っていて、返信の下書きも用意されている

**〔参考・今回は実装しない〕B3. 月末の請求書づくり**（今のデモの発展版）
- いつもの月末（例：3時間）：取引明細を顧客ごとにまとめる → 請求書に宛名と金額を転記 → PDFにして送付準備
- 組み合わせ：明細の集計（プログラム）＋請求書PDFの作成（既存の `invoicePdf.ts`）＋送付メールの下書き（AI）
- 人が確認：前月から金額が大きく変わった顧客
- 結果（例）：3時間 → 15分
- ルーチン化：月末の朝に、全顧客分の請求書PDFの下書きとチェック表がそろっている
- 備考：「毎日」ではなく「毎月」なので、⑤は「毎月末の朝」になる

#### C. 問い合わせに対応する人（連絡・対応）

**★C1. 問い合わせの振り分けと一次返信**（今のデモの発展版）
- いつもの朝（例：60分）：フォームとメールに届いた問い合わせを全部読む → 内容ごとに担当者へ転送 → 一次返信を書く → 返信漏れがないか確認
- 組み合わせ：問い合わせの取り込み＋種別の判定（フォームの項目はルール、自由記述はAIが候補を出す）＋担当者への通知＋一次返信の下書き（AI）＋未対応の一覧
- 人が確認：AIが種別を決めきれなかったもの、クレームの可能性があるもの
- 結果（例）：60分 → 10分
- ルーチン化：出社すると担当ごとに振り分け済みで、返信の下書きがメールの下書きフォルダに入っている（送信は人が行う）

**〔参考・今回は実装しない〕C2. 朝の「今日やること」まとめ**
- いつもの朝（例：40分）：夜のうちに届いたメールとチャットを読む → カレンダーで今日の予定を確認 → 今日やることをメモにまとめる
- 組み合わせ：未読メール・チャット・予定の取り込み＋要約と優先順位づけ（AI）＋チャットへの通知
- 人が確認：AIが「返信が必要」と判断したものが本当にそうか
- 結果（例）：40分 → 5分
- ルーチン化：毎朝8:00に「今日の予定と、対応が必要な3件」がチャットに届く
- 備考：誰にでも伝わる題材。「AIにどこまでメールを読ませてよいか」というルールづくりの話にもつなげやすい

**〔参考・今回は実装しない〕C3. 日程調整と前日リマインド**
- いつもの朝（例：30分）：商談や面接の候補日をメールでやり取り → 決まったら予定に登録 → 前日にリマインドを送る
- 組み合わせ：カレンダーの空き時間の抽出＋候補日メールの下書き（AI）＋前日リマインドの下書き
- 人が確認：先方の返信があいまいなケース（「来週ならいつでも」など）
- 結果（例）：30分 → 5分
- ルーチン化：毎朝、翌日の予定の相手へのリマインド下書きがそろっている
